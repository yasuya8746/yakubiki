# ADR-0002: 薬剤データ収集の実行場所(端末 or サーバ側バッチ)

- 日付: 2026-10-26(第1版)/ 2026-10-26(第2版 追記)
- ステータス: 承認済み(2026-10-28 人間が承認)
- 関連: `docs/requirements/drug-search-beta.md`, ADR-0001, ADR-0004

> **第2版で前提と決定を変更した。** ADR-0001 第2版により、本文(添付文書)を持たないリンク方式になり、取得元は厚労省の公開ファイルに変わった。
> 現行の提案は末尾の「第2版(2026-10-26 追記): リンク方式での再比較」を参照。第1版の本文は経緯として残し、書き換えない。

## 背景
- 要望: 「薬剤情報は1日1回ネットから集めてアプリ内に保存する」。
- 取得元は ADR-0001 で PMDA 添付文書情報(+公的マスタ)を推奨。取得元は HTML/XML/PDF などで、整形・解析が必要。
- 規模の見込み(要スパイク確認): 医療用医薬品は約1.5〜2万品目。添付文書XMLは1件あたり数十〜数百KB。必要項目のみ抽出・テキスト化すると1品目あたり数KB〜十数KBで、全体で数十〜数百MB(未圧縮)。一般名単位で同一内容をまとめれば大きく減らせる見込み。
- 制約: 開発1か月、ログインなし、取得元に過大な負荷をかけない、規約に従う。

## 選択肢
| 案 | 概要 |
|---|---|
| A | 端末で直接収集: 各端末の WorkManager が1日1回、取得元から直接ダウンロード・解析して Room に保存 |
| B | サーバ側バッチ+静的配信: 1日1回のバッチ(例: GitHub Actions のスケジュール実行 / Cloud Run Jobs)が取得・解析・整形し、データ版(圧縮済み SQLite もしくは JSON、差分ファイル、メタ情報)を静的ホスティング(Cloud Storage / Firebase Hosting 等)へ配置。アプリは WorkManager+Retrofit で1日1回メタ情報を確認し、新しければダウンロードして Room に取り込む |
| C | サーバ側バッチ+API サーバ: B と同様に収集するが、検索APIを持つバックエンドを立て、アプリは都度問い合わせ(+キャッシュ) |
| D | 初期データ同梱+B の差分同期: B に加え、APK にスナップショットを同梱して初回のダウンロードを不要にする |

### 比較
| 観点 | A: 端末で収集 | B: バッチ+静的配信 | C: バッチ+APIサーバ | D: 同梱+B |
|---|---|---|---|---|
| データ量(端末通信) | 大。解析前の原データ(数百MB〜GB級)を各端末が取得しうる | 小〜中。初回は整形済み圧縮データ(数十MB目標)、以降は差分(多くの日は数KB〜数MB) | 小(都度)。ただしオフライン要件のため結局キャッシュが必要 | 最小(初回ダウンロード不要) |
| 端末への負荷 | 大。解析処理・電池・ストレージ一時領域。WorkManager の実行時間制限(長時間処理は中断されうる)にも抵触しやすい | 小。ダウンロードとDB取り込みのみ | 小 | 小(ただしAPKサイズ増) |
| 取得元への負荷 | **端末数 × 全件**。100台なら100倍。規約・マナー上ほぼ不可 | **1日1回 × 1プロセス**。差分取得・レート制限を一元管理できる | B と同じ | B と同じ |
| 規約面 | 各端末が自動取得=規約違反リスクが最大。ユーザー(医療従事者)をリスクに巻き込む | 取得主体が運営者に一本化され、説明・許諾取得・停止がしやすい | B と同じ。ただしAPIは誰でも叩ける状態になりやすい | B と同じ。APKに本文を含めるとストア経由の再配布にもなる点は要確認 |
| 品質管理 | 端末ごとに結果がばらつく。解析バグの修正にアプリ更新が必要 | サーバで検証(件数チェック等)してから公開できる。解析修正はアプリ更新不要 | B と同じ | B と同じ |
| オフライン | ○ | ○(全件を端末DBに保持) | △(キャッシュ設計が別途必要) | ◎(初回から使える) |
| 運用・費用 | サーバ不要 | スケジュール実行+静的ホスティング。ほぼ無料〜少額 | サーバ常時運用・監視・スケール。費用・作業が増える | B と同じ+APK更新でスナップショット更新 |
| 1か月で作れるか | △ 解析処理を Kotlin/Android 上で作る必要があり、端末差・実行制限への対処で膨らむ | ○ バッチは単純な ETL、アプリは「ダウンロード→取り込み」のみ | △ API・認可・監視まで含めると厳しい | ○ B に同梱処理を足す程度(+0.5〜1日) |
| 取得元変更への強さ | 弱(アプリ更新が必要) | 強(バッチのみ修正) | 強 | 強 |

### テンプレート形式の要約
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A | サーバ不要 | 端末負荷・通信量大、実装が複雑 | 取得元への過大負荷・規約違反、取得元変更でアプリ全台が停止 |
| B | 端末負荷小、取得元負荷最小、品質ゲートを置ける、1か月で現実的 | バッチと配信基盤の運用が必要 | 配信URLが漏れると第三者もデータを取得できる(ログインなしのため) |
| C | 検索ロジックをサーバで改善可能 | 常時運用・費用、オフラインに追加設計 | 期間超過、APIの無認可公開 |
| D | 初回からオフラインで使える | APKサイズ増、同梱データが古くなる | 同梱=ストア経由の再配布となり規約面の確認が増える |

## 決定(提案)
- **案B(サーバ側バッチ+静的配信、アプリは1日1回同期)を推奨**。D(同梱)はβではスコープ外とし、初回はダウンロードで取得する(APKサイズと規約確認を増やさないため)。
- 実装方針(案):
  - バッチ: 1日1回(深夜帯)実行。取得元の更新一覧から差分を取り、必要分のみ取得。リクエスト間隔を空ける(例: 数秒に1件)、User-Agent に連絡先、失敗時は前日データを維持。
  - 品質ゲート: 品目数が前日比で一定以上(例: 5%超)減少、または解析失敗率が閾値超過のときはデータ版を公開せず、運用者に通知。
  - 配信物: `manifest.json`(データ版ID、生成日時、件数、ファイルのハッシュ)+フルデータ(圧縮 SQLite もしくは JSON)+差分(任意。βではフル置換のみでも可。データ量がスパイクで大きいと判明したら差分を導入)。
  - アプリ: WorkManager の PeriodicWork(24時間、ネットワーク接続かつバッテリー低下でない)で manifest を Retrofit で取得 → 新しければダウンロード → ハッシュ検証 → Room に別テーブル/別DBで取り込み → トランザクションで切替。
  - 配信先のアクセス制限: ログインがないため完全な制限は不可。推測されにくいURL+(必要なら)アプリ固定の簡易トークン程度とする。**これは秘匿性を保証しない**ことを前提とし、配信データは「取得元で公開されている情報」に限る。ライセンスデータ(ADR-0001 案B/C)を扱う場合は認可の仕組みを別ADRで再検討する。
- 実行基盤の第一候補は GitHub Actions のスケジュール実行(既に `.github/workflows/` がありCIと統一できる)。ただしスケジュール実行の遅延・実行時間上限・リポジトリの公開状態に注意。不十分なら Cloud Run Jobs 等へ移す(要人間判断: クラウドアカウント・費用)。

## 影響・結果
- 要望3の「1日1回ネットから集めてアプリ内に保存」は「サーバが1日1回集めて整形し、アプリは1日1回取り込んで端末に保存する」と解釈を変える。**人間の承認が必要**。
- リポジトリ構成に、アプリとは別のバッチ用ディレクトリ(例: `batch/`)が加わる(言語は Kotlin/JVM を第一候補にしてモデル共有を図る。決定は実装着手時)。
- ops 担当が日次バッチの監視・失敗時対応の runbook を作る。
- 配信基盤のアカウント・シークレット(デプロイ用認証情報)は CI シークレットで管理し、リポジトリに含めない。

## 第2版(2026-10-26 追記): リンク方式での再比較

### 前提の変化
| 項目 | 第1版 | 第2版 |
|---|---|---|
| 取得元 | PMDA 添付文書(HTML/XML/PDF) | 厚労省 薬価基準収載品目リスト(Excel 数ファイル)。PMDA には自動アクセスしない |
| 保持する内容 | 本文(用途・成分・副作用・併用禁忌) | 検索インデックスのみ(品名・成分名・規格・区分・メーカー・コード・リンク情報) |
| データ量(見込み) | 数十〜数百MB | 約2万品目 × 1件あたり数百バイト = **数MB(未圧縮)、圧縮後1〜2MB程度**(T02 で実測) |
| 整形の負荷 | 大(セクション抽出・併用禁忌表の解析) | 小(Excel の列を読み、名称を正規化し、リンク用コードを作る) |
| 元データの更新頻度 | ほぼ毎営業日 | **おおむね月次以下**(薬価改定・新薬収載・後発品収載など。ADR-0001 第2版) |
| すぐ直す必要があるもの | 本文の誤り | **リンク切れ・誤リンク**(PMDA の規約上、速やかな修正義務がある。ADR-0004) |

第1版で案Aを退けた最大の理由(取得元への負荷・端末での解析)は、元データが小さく PMDA に触れないため弱まった。一方で「リンクの修正をアプリ更新なしで速やかに配りたい」という新しい要求が加わった。

### 選択肢(第2版)
| 案 | 概要 |
|---|---|
| E1 | **同梱のみ**: 変換済みインデックス(SQLite)を APK に同梱する。元データの更新やリンク修正は、アプリの新しいビルドを内部テストで配って反映する。サーバなし |
| E2 | **同梱+静的配信での差し替え(更新確認はスケジュール実行)**: APK に初期インデックスを同梱。サーバ側の小さなジョブ(GitHub Actions)が1日1回、厚労省のページを確認し、更新があれば Excel を取得・変換・検証して静的ホスティングに置く。アプリは1日1回 manifest を確認し、新しければ差し替える |
| E3 | **同梱+静的配信での差し替え(更新は手動起動)**: E2 と同じ配信の仕組みだが、ジョブは人が起動する(厚労省の更新に気づいたとき・リンクを直すとき) |
| E4 | **端末が厚労省から直接取得**: 各端末が1日1回、厚労省のページを確認して Excel を取得・変換する(第1版の案A に相当) |

### 比較(第2版)
| 観点 | E1: 同梱のみ | E2: 同梱+配信(日次自動確認) | E3: 同梱+配信(手動起動) | E4: 端末で直接取得 |
|---|---|---|---|---|
| 初回からオフラインで使えるか | ◎ | ◎ | ◎ | ×(初回取得が必要) |
| リンク修正の速さ(ADR-0004) | △ ビルド→内部テスト配信→Play の自動更新まで数日。利用者が更新しないと直らない | ◎ 配信の差し替えだけ。端末には最長24時間で届く | ◎ 同左 | △ リンク表をどこかに置く必要があり、結局サーバが要る |
| 元データ更新への追従 | △ 人が気づいてビルド・配信 | ◎ 自動(1日以内) | ○ 人が気づけば即時 | ◎ |
| 取得元へのアクセス | 人が手作業でダウンロード | **1日1回1ページ+更新時のみ数ファイル**(1プロセス) | 人が起動した時のみ | 端末数 × 1日1回。100台なら100倍。Excel 解析も端末で行う |
| 規約面 | 最も安全 | 厚労省サイトに自動取得の制限が無いことの確認が必要(ADR-0001 第2版 確認事項2) | E1 と同等に安全 | 利用者の端末から自動取得させることになり、説明が難しい |
| 運用・費用 | 配信基盤なし。ただし更新のたびにリリース作業(release-manager・人間) | GitHub Actions+静的ホスティング(無料〜少額)。ジョブ失敗の通知 | E2 と同じ基盤。起動を忘れるリスク | サーバ不要。ただしリンク表の置き場が要る |
| 実装量(developer) | 変換スクリプト+同梱で **約2日** | E1 に加えて、配信ジョブ・manifest・同期 Worker で **+約2.5日** | E2 とほぼ同じ(スケジュール設定が無いだけ) | 端末上で Excel 解析(Apache POI 等で APK 肥大)、**約4日以上** |
| 将来性 | 小さい規模なら十分 | 一般公開時もそのまま使える | E2 に切り替えやすい | 弱い |

### テンプレート形式の要約(第2版)
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| E1 | 最も簡単。サーバ・シークレット不要 | リンク修正・データ更新にアプリのリリースが要る | PMDA の移動時に「速やかに修正」を満たせない。利用者が古い版を使い続ける |
| E2 | 自動で追従。リンクを即日直せる | 配信基盤とジョブの運用 | 厚労省ページの URL・列構成の変更でジョブが失敗(品質ゲートで止める) |
| E3 | E2 の利点のうちリンク修正の速さは維持。規約確認前でも始められる | 元データの更新に人が気づく必要 | 起動忘れでインデックスが古くなる |
| E4 | サーバ不要 | 端末負荷・APK 肥大・初回オフライン不可 | 取得元への負荷が端末数倍。リンク修正の手段が別に要る |

### 「サーバ側バッチは本当に必要か」への回答
- **本文の取得・解析のためのバッチは不要になった。** 処理は「Excel を変換する」だけで、数秒〜数十秒で終わる。
- **ただし配信の仕組み(静的ホスティング+manifest+アプリの同期)は残すべき**。理由は、PMDA の規約にある「リンク先が移動したら速やかに修正する」義務を、アプリのリリースなしで果たすため(E1 ではリリースと利用者側の更新を待つことになる)。
- 自動の日次確認(E2)と手動起動(E3)の差は小さい。同じジョブに「スケジュール実行」を足すかどうかだけである。

### 決定(提案・第2版)
1. **E3 で始め、T01 で厚労省サイトの利用条件(自動取得の制限が無いこと)が確認できたら E2 に切り替える**(ジョブの `schedule` を有効にするだけ)。第1版の案B(PMDA 本文を処理するバッチ)は撤回する。
2. 構成:
   - 変換ジョブ(GitHub Actions。`workflow_dispatch` で手動起動。E2 移行後は1日1回の `schedule` を追加):
     1. 厚労省の公開ページを1回取得し、掲載ファイルの更新日・ファイル名・ハッシュが前回と同じなら終了(manifest の「最終確認日時」だけ更新)。User-Agent に連絡先を入れる。
     2. 変わっていれば Excel(数ファイル)を取得し、品目表に変換する(名称のかな・全半角正規化、薬価列は捨てる、リンク方式の決定)。
     3. 品質ゲート: 品目数が前回比で一定以上(例: 5%超)減った、必須列が見つからない、などの場合は公開せず通知する。
     4. 静的ホスティングに配置: `manifest.json`(データ版ID、元データの公表日/適用日、生成日時、最終確認日時、件数、ハッシュ、スキーマ版、**URL テンプレート**)、インデックス(圧縮 SQLite)、**リンク上書き表**(ADR-0004)。
     - リンク上書き表と URL テンプレートだけを直す場合は、Excel を取得せずに配信できるようにする(リンク修正を速くするため)。
   - アプリ:
     - 初期インデックスとテンプレートを APK に同梱し、初回起動から通信なしで検索できる。
     - WorkManager の PeriodicWork(24時間、ネットワーク接続時)で manifest を Retrofit で取得し、新しければダウンロード→ハッシュ検証→別DBに取り込み→切替。リンク上書き表だけの更新は小さいファイルで済む。
     - データは数MB規模なので、差分配信は作らない(常にフル置換)。
   - 配信先: 第1版と同じく、公開情報だけを置く(秘匿性は不要)。デプロイ用の認証情報は CI シークレットで扱う。
3. 同梱データの更新: アプリのリリース時に、その時点の最新インデックスを同梱し直す(ビルド時に配信データを取り込むか、変換ジョブの出力を使う)。
4. 第1版で「スコープ外」としていた案D(同梱)は、データが小さくなり規約上の懸念(本文の再配布)も無くなったため、**採用に変える**。

### 影響・結果(第2版)
- 要望3「1日1回ネットから集めてアプリ内に保存」は、次のように読み替える(**人間の承認が必要**)。
  - 「サーバが厚労省の公開リストの更新を確認し(β開始時は手動、規約確認後は1日1回)、更新があればインデックスを作り直す。アプリは1日1回、新しいインデックスとリンク情報があるかを確認して端末に保存する。添付文書の本文は保存しない」。
- 第1版の T06〜T08(取得・解析・品質ゲート)は、変換ジョブ1本(約1.5日)と配信(約1日)に縮む。
- ops の runbook は「変換ジョブの失敗・品質ゲート不合格時の対応」「リンク修正の配信手順」「配信停止」を扱う。
- `batch/` ディレクトリは変換スクリプト用として残す(言語は Kotlin/JVM 第一候補のまま。Excel 読み込みライブラリの選定は実装時)。

## 追記(2026-10-30): 配信形式の変更
- 第2版の「インデックス(圧縮 SQLite)」は、ADR-0005 で「品目表(gzip JSON)を端末で取り込む」形式に置き換えた。manifest のファイル名も `manifest.json` から、スキーマ版付きの `manifest-v1.json` に変えた。理由と manifest・上書き表の形式は ADR-0005 を参照。
