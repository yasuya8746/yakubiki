# ADR-0005: 品目表・manifest・リンク上書き表の形式(データモデルと配信フォーマット)

- 日付: 2026-10-30
- ステータス: 提案
- 関連: `docs/requirements/drug-search-beta.md`(FR-1〜FR-4、FR-8), ADR-0001, ADR-0002 第2版, ADR-0004(D12 決定), ロードマップ T05

## 背景
- T02 で次のことが分かった(ADR-0001・ADR-0004 の 2026-10-30 追記)。
  - 厚労省の薬価基準収載品目リストは区分ごとの Excel(内用 7,073・注射 3,479・外用 1,862、計 12,414 品目)。コードは12桁で重複なし。YJコード列・読み(カナ)列は無い。
  - メーカー名のある品目はリストのコードで L1(rdSearch)が開く。メーカー名が空欄の品目(1,591、12.8%)は L1 で「該当なし」になり、L2(成分一覧 `GeneralList/[コード上7桁]`)を使う(D12 決定)。
  - PMDA の検索画面(L3)は検索語を URL で渡せない。
  - 区分ごとに元データの適用日が違うことがある(外用薬だけ 10月14日版が最新)。
- T06(変換ジョブ)・T08(アプリの DB と検索)・T09(同期)・T11(リンク)が共通で使う形をここで決める。
- 試作の変換(標準ライブラリのみ、リポジトリ外)で実測したサイズ: 12,414 品目の JSON が約 2.7MB、gzip 後 **約 230KB**。非機能要件の目標(圧縮後 2MB 以内)に十分収まる。

## 選択肢

### 1. 品目表の配信形式
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: 圧縮 SQLite を配り、端末で DB ファイルごと差し替える(ADR-0002 第2版の当初案) | 取り込み処理が要らない | 変換ジョブで Room と同じスキーマの SQLite を作る必要がある。Room の DB を実行中に差し替えるのは難しい(接続を閉じて開き直す) | Room のスキーマ版と配信物の版がずれると起動できない |
| B: gzip した JSON を配り、端末で Room の別テーブルに取り込んでから切り替える | 変換ジョブは言語を問わず単純。項目の追加に強い(未知の項目は無視できる)。検証しやすい | 取り込み処理(1万件強の挿入)が要る。実測規模なら1秒程度の見込み | 取り込み中断時の後始末が要る(別テーブルに入れてから一括切替で防ぐ) |

### 2. 検索方式
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: Room FTS(ロードマップ T08 の当初案) | 大規模でも速い | 標準のトークナイザは日本語の部分一致に向かない(単語区切りが無い) | 「ロキソ」で「ロキソニン」が出ないなど、FR-1.1 の部分一致を満たせない |
| B: 正規化した検索用文字列への `LIKE '%語%'` | FR-1.1 の部分一致をそのまま満たす。仕組みが単純 | 全件走査になる | 1.2万件・1件100文字程度なので、300ms 以内(非機能要件)に収まる見込み。T08 で実測する |

### 3. 検索用文字列(正規化済み名称)を作る場所
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: 変換ジョブで作って配信する | 端末の処理が減る | 配信サイズが約3割増える。入力側の正規化と別の実装になる | ジョブとアプリの正規化がずれると検索漏れが起きる |
| B: 端末で取り込み時に作る | 入力と索引を同じコードで正規化でき、ずれない | 正規化の規則を変えるとアプリ更新が要る | 小さい(規則の変更はまれ) |

## 決定(提案)
1. **品目表は gzip JSON(案1-B)で配り、端末で別テーブルに取り込んでから一括で切り替える。** 同梱データも同じ形式のファイルを APK の assets に入れ、初回起動時に同じ処理で取り込む(取り込みの経路を1本にする)。
2. **検索は正規化済み文字列への部分一致(案2-B)とし、FTS は使わない。** T08 で 300ms 以内を実測し、満たさなければ見直す。ロードマップ T08 の「FTS 検索 DAO」はこの決定で置き換える。
3. **検索用文字列は端末で作る(案3-B)。** 配信データには入れない。
4. 以下の形式を採用する。

### 4.1 品目表(`items.json.gz`)
厚労省リストの1行を1品目とする。薬価・経過措置・備考・局/麻の印は持たない(ADR-0002)。

| 項目 | 型 | 必須 | 内容 |
|---|---|---|---|
| `code` | 文字列(12桁) | ○ | 薬価基準収載医薬品コード。主キー |
| `category` | 列挙 | ○ | `ORAL`(内用薬) / `INJECTION`(注射薬) / `EXTERNAL`(外用薬) / `DENTAL`(歯科用薬剤) |
| `name` | 文字列 | ○ | 品名。NFKC 正規化済み(英数字・記号を半角に。PMDA の表示と見比べやすくするため) |
| `ingredient` | 文字列 | ○ | 成分名。NFKC 正規化済み |
| `spec` | 文字列 | ○ | 規格。NFKC 正規化済み |
| `maker` | 文字列 / null | | メーカー名。空欄は null |
| `brand` | 列挙 / null | | `BRAND`(先発品) / `QUASI_BRAND`(準先発品) / null |
| `generic` | 列挙 / null | | `GENERIC`(印「後発品」) / `GENERIC_STAR`(印「★」) / null。画面ではどちらも「後発品」と表示する。印の意味の違いは T06 で厚労省の説明を確認する |
| `link` | 列挙 | ○ | 主ボタンの既定方式。`L1`(メーカー名あり) / `L2`(メーカー名が空欄)。変換ジョブが決める(D12) |

```json
{"schemaVersion":1,"items":[
 {"code":"1149019C1157","category":"ORAL","name":"ロキソプロフェンNa細粒10%「サワイ」",
  "ingredient":"ロキソプロフェンナトリウム水和物","spec":"10%1g","maker":"メディサ新薬",
  "brand":null,"generic":"GENERIC_STAR","link":"L1"}]}
```

- 将来の項目(読み `kana`、YJコード `yjCode` など)は、**null を許す項目の追加**で足す。アプリは未知の項目を無視する。項目の追加は `schemaVersion` の更新を伴わない。意味が変わる変更(必須項目の削除・型の変更)だけ `schemaVersion` を上げる。
- アプリは自分が扱えない `schemaVersion` のデータを取り込まず、手元のデータを使い続ける。

### 4.2 検索用文字列(端末で作る)
`品名 + 成分名` に次の処理をした文字列を、品目ごとに Room に保存する。検索語にも同じ処理をする。
1. NFKC 正規化(全角英数字→半角、半角カナ→全角カナ)
2. 英字を小文字に
3. ひらがなをカタカナに
4. 空白をすべて除く

「ろきそ」「ロキソ」「ﾛｷｿ」はすべて「ロキソ」になる。漢字名称の読み検索は対象外(FR-1.2 の制約のまま)。

### 4.3 リンク上書き表(`link-overrides.json`)
ADR-0004 の「リンク上書き表」。品目ごとに既定のリンクを上書きする。

| 項目 | 内容 |
|---|---|
| `code` | 対象の品目コード |
| `mode` | `L1` / `L2` / `URL`(固定 URL を使う) / `SEARCH_ONLY`(主ボタンを出さず副ボタンだけ。FR-2.5) |
| `url` | `mode` が `URL` のときだけ。固定の URL |
| `reason` | 上書きの理由(運営者向けのメモ。画面には出さない) |
| `updatedAt` | 更新日(ISO 8601) |

```json
{"schemaVersion":1,"overrides":[
 {"code":"1112700X1011","mode":"SEARCH_ONLY","reason":"成分一覧が空(T02 確認)","updatedAt":"2026-10-30"}]}
```

- 表に無い品目は、品目表の `link` を使う。
- 初期の上書き表は空とし、T02 で空の一覧を確認したハロタンだけ `SEARCH_ONLY` にする。それ以外の空の一覧は、報告と定期確認で見つけて足す(ADR-0004)。

### 4.4 manifest(`manifest.json`)
アプリが1日1回取得する小さなファイル(数KB)。

```json
{
  "schemaVersion": 1,
  "dataVersion": "20261101-01",
  "generatedAt": "2026-11-01T03:00:00+09:00",
  "lastCheckedAt": "2026-11-02T03:00:00+09:00",
  "sources": [
    {"category": "ORAL",      "fileName": "tp20261101-01_01.xlsx", "appliedDate": "2026-11-01", "sha256": "…"},
    {"category": "INJECTION", "fileName": "tp20261101-01_02.xlsx", "appliedDate": "2026-11-01", "sha256": "…"},
    {"category": "EXTERNAL",  "fileName": "tp20261014-01_03.xlsx", "appliedDate": "2026-10-14", "sha256": "…"}
  ],
  "itemCount": {"ORAL": 7073, "INJECTION": 3479, "EXTERNAL": 1862},
  "files": {
    "items":         {"path": "items-20261101-01.json.gz", "sha256": "…", "size": 233813},
    "linkOverrides": {"path": "link-overrides-0001.json",  "sha256": "…", "size": 180}
  },
  "urlTemplates": {
    "l1": "https://www.pmda.go.jp/PmdaSearch/rdSearch/02/{code}?user=1",
    "l2": "https://www.pmda.go.jp/PmdaSearch/iyakuDetail/GeneralList/{code7}",
    "l3": "(PMDA の検索画面の URL。T11 の前に人が確認する)"
  }
}
```

- `sources` は区分ごとに適用日を持つ(区分ごとに更新日が違うため)。検索画面の「データ版」表示(FR-4.1)は区分ごとの適用日を出すか、最も古い日を出すかを T10 で決める。
- `lastCheckedAt` は、元データに変化が無くても変換ジョブが確認するたびに更新する(FR-4.2)。
- ファイルは版ごとに別の名前で置き、manifest だけを最後に差し替える(取得途中の端末が新旧の混ざったファイルを読まないため)。
- アプリは `files` の `sha256` が手元と違うファイルだけを取得し、ハッシュを検証してから取り込む。**上書き表だけの更新(リンク修正)は数百バイトの取得で済む**(FR-8.1)。

### 4.5 URL の組み立てと検証(アプリ)
- 置き換える記号は `{code}`(12桁)と `{code7}`(上7桁)だけ。
- 主ボタンの URL は「上書き表 → 品目表の `link` → テンプレート」の順に決める。副ボタン(L3)は全品目に出す。
- **配信された URL テンプレートと固定 URL は、`https://www.pmda.go.jp/` で始まるものだけを使う。** それ以外なら同梱の既定値に戻す(配信データが壊れたり差し替えられたりしても、利用者を別のサイトへ送らないため)。
- テンプレートの既定値はアプリにも同梱する。アプリのコードに PMDA の URL を書くファイルは、そのとき `scripts/ci/pmda-allowlist.txt` に1行で追加する(T04 の検査)。

### 4.6 変換ジョブの品質ゲート(T06・T07 で実装)
次のどれかに当てはまれば公開せず、運営者に通知する。
- 期待する見出し(区分・コード・成分名・規格・品名・メーカー名・先発/後発の列)が位置どおりに見つからない(ふりがな付きの見出しは、ふりがなを除いて照合する)
- コードが12桁でない、または重複がある
- 区分ごとの件数が前回より 5% を超えて減った
- `link` が `L1` の品目の割合が前回から 5 ポイントを超えて変わった

## 影響・結果
- ロードマップ T08 の「Room スキーマ+FTS 検索 DAO」は「Room スキーマ+部分一致検索 DAO」に変わる。
- ADR-0002 第2版の「インデックス(圧縮 SQLite)」は「品目表(gzip JSON)」に置き換わる。
- 同梱データのサイズは約 230KB(gzip)で、APK への影響は小さい。
- 歯科用薬剤のファイルは T02 で調べていない(区分の列挙には入れておく)。T06 で厚労省ページに歯科用薬剤のファイルがあるかを確かめる。
- 人が確認する事項: L3(PMDA の検索画面)の URL。T11 の前に、ブラウザで検索画面を開いて URL を記録する。
- 配信先(D4)が決まるまでは、manifest の置き場所は未定。アプリは配信元の URL をビルド設定で持つ。
