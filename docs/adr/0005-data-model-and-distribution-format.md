# ADR-0005: 品目表・manifest・リンク上書き表の形式(データモデルと配信フォーマット)

- 日付: 2026-10-30
- ステータス: 提案
- 関連: `docs/requirements/drug-search-beta.md`(FR-1〜FR-4、FR-8), ADR-0001, ADR-0002 第2版, ADR-0004(D12 決定), ロードマップ T05

## 背景
- T02 で次のことが分かった(ADR-0001・ADR-0004 の 2026-10-30 追記)。
  - 厚労省の薬価基準収載品目リストは区分ごとの Excel(内用 7,073・注射 3,479・外用 1,862、計 12,414 品目)。コードは英数字12文字で重複なし。YJコード列・読み(カナ)列は無い。
  - メーカー名のある品目はリストのコードで L1(rdSearch)が開く。メーカー名が空欄の品目(1,591、12.8%)は L1 で「該当なし」になり、L2(成分一覧 `GeneralList/[コード上7桁]`)を使う(D12 決定)。
  - PMDA の検索画面(L3)は検索語を URL で渡せない。
  - 区分ごとに元データの適用日が違うことがある(外用薬だけ 10月14日版が最新)。
- T06(変換ジョブ)・T07(配信)・T08(アプリの DB と検索)・T09(同期)・T11(リンク)が共通で使う形をここで決める。
- 試作の変換(標準ライブラリのみ、リポジトリ外)で実測したサイズ: 12,414 品目の JSON が約 2.7MB、gzip 後 **約 230KB**。非機能要件の目標(圧縮後 2MB 以内)に十分収まる。

## 選択肢

### 1. 品目表の配信形式
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: 圧縮 SQLite を配り、端末で DB ファイルごと差し替える(ADR-0002 第2版の当初案) | 取り込み処理が要らない | 変換ジョブで Room と同じスキーマの SQLite を作る必要がある。Room の DB を実行中に差し替えるのは難しい(接続を閉じて開き直す) | Room のスキーマ版と配信物の版がずれると起動できない |
| B: gzip した JSON を配り、端末で Room の別テーブルに取り込んでから切り替える | 変換ジョブは言語を問わず単純。項目の追加に強い(未知の項目は無視できる)。検証しやすい | 取り込み処理(1万件強の挿入)が要る。実測規模なら1秒程度の見込み | 取り込み中断時の後始末が要る(別テーブルに入れてから一括切替で防ぐ) |

### 2. 検索方式
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: Room FTS(ロードマップ T08 の当初案) | 大規模でも速い | 標準のトークナイザは日本語の部分一致に向かない(単語区切りが無い) | 「ロキソ」で「ロキソニン」が出ないなど、FR-1.1 の部分一致を満たせない |
| B: 正規化した検索用文字列への部分一致(`instr`) | FR-1.1 の部分一致をそのまま満たす。仕組みが単純 | 全件走査になる | 1.2万件・1件100文字程度なので、300ms 以内(非機能要件)に収まる見込み。T08 で実測する |

### 3. 検索用文字列(正規化済み名称)を作る場所
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: 変換ジョブで作って配信する | 端末の処理が減る | 配信サイズが約3割増える。入力側の正規化と別の実装になる | ジョブとアプリの正規化がずれると検索漏れが起きる |
| B: 端末で取り込み時に作る | 入力と索引を同じコードで正規化でき、ずれない | 正規化の規則を変えるとアプリ更新が要る | 小さい(規則の変更はまれ) |

### 4. 配信データの改ざん対策
| 案 | メリット | デメリット | リスク |
|---|---|---|---|
| A: HTTPS と配信基盤の書き込み権限の制限だけ | 追加実装なし | 配信基盤や CI が乗っ取られると、品名とコードの対応を差し替えて**PMDA 内の別の薬のページ**へ送れる(URL の検証では防げない) | 誤リンク(医療安全)。気づくのは利用者の報告頼み |
| B: A に加えて manifest に署名(Ed25519)。公開鍵をアプリに同梱し、署名済み manifest のハッシュで各ファイルを検証する | 配信基盤だけが乗っ取られても改ざんを検知できる | 実装 約0.5日。署名鍵の保管(CI シークレット)と、鍵を失ったときの手順が要る | 署名鍵の漏えい・紛失(紛失時は公開鍵を変えたアプリの更新が要る) |

## 決定(提案)
1. **品目表は gzip JSON(案1-B)で配り、端末で別テーブルに取り込んでから一括で切り替える。**
2. **検索は正規化済み文字列への部分一致(案2-B)とし、FTS は使わない。** T08 で 300ms 以内を実測し、満たさなければ見直す。
3. **検索用文字列は端末で作る(案3-B)。** 配信データには入れない。
4. **改ざん対策は案4-B(manifest の署名)を推奨する。** 理由は、誤リンクが医療安全に直結し、受け入れ条件が「誤リンク0件」であるため。β で入れない場合は、案4-A のリスクを受け入れることを人間の判断として記録する(**D13 として人間が決める**)。
5. 以下の形式を採用する。

### 5.1 品目表(`items.json.gz`)
厚労省リストの1行を1品目とする。薬価・経過措置・備考・局/麻の印は持たない(ADR-0002)。

| 項目 | 型 | 必須 | 内容 |
|---|---|---|---|
| `code` | 文字列 | ○ | 薬価基準収載医薬品コード。英数字12文字(`^[0-9A-Z]{12}$`)。主キー |
| `category` | 列挙 | ○ | `ORAL`(内用薬) / `INJECTION`(注射薬) / `EXTERNAL`(外用薬) / `DENTAL`(歯科用薬剤) |
| `name` | 文字列 | ○ | 品名(空でない) |
| `ingredient` | 文字列 | ○ | 成分名(空でない) |
| `spec` | 文字列 | ○ | 規格(空でない) |
| `maker` | 文字列 / null | | メーカー名。空欄は null |
| `brand` | 列挙 / null | | `BRAND`(先発品) / `QUASI_BRAND`(準先発品) / null |
| `generic` | 列挙 / null | | `GENERIC`(印「後発品」) / `GENERIC_STAR`(印「★」) / null。画面ではどちらも「後発品」と表示する。印の意味の違いは T06 で厚労省の説明を確認する |
| `defaultLink` | 列挙 | ○ | 主ボタンの既定方式。`L1`(メーカー名あり) / `L2`(メーカー名が空欄)。変換ジョブが決める(D12) |

- 表示用の `name`・`ingredient`・`spec` は、元データから**前後の空白を除き、全角英数字・記号(U+FF01〜U+FF5E)だけを半角にした**ものとする。NFKC 全体は使わない(「㎎→mg」「Ⅱ→II」「①→1」など公式の表記まで変わり、PMDA の表示と見比べる確認(FR-2.4)を難しくするため)。T02 で見た PMDA の表示(`Na`、`10%`)は半角だった。
- 変換ジョブは、`code` の形式と必須項目が空でないことを検証し、合わない行があれば公開しない(5.6)。アプリも取り込み時に同じ検証をし、合わない行は取り込まない。

```json
{"items":[
 {"code":"1149019C1157","category":"ORAL","name":"ロキソプロフェンNa細粒10%「サワイ」",
  "ingredient":"ロキソプロフェンナトリウム水和物","spec":"10%1g","maker":"メディサ新薬",
  "brand":null,"generic":"GENERIC_STAR","defaultLink":"L1"}]}
```

### 5.2 版の扱い(スキーマ版)
- 各ファイルのスキーマ版は **manifest の `files` 側に持つ**(ダウンロード前に判定できるようにする)。manifest 自体の版は、manifest のファイル名で表す(`manifest-v1.json`)。
- アプリは、自分が扱えるスキーマ版の manifest(`manifest-v1.json`)だけを取得する。
- **互換を壊さない変更**(スキーマ版はそのまま):
  - null を許す項目の追加。アプリは未知の項目を無視する。
  - 列挙値の追加。アプリは未知の値を、その品目では `SEARCH_ONLY`(主ボタンを出さず副ボタンだけ)として扱う。
- **互換を壊す変更**(必須項目の削除・型や意味の変更)はスキーマ版を上げ、`manifest-v2.json` を新設する。**旧版の manifest とファイルも、旧アプリが残る間は並行して配信し続ける**(更新していない端末にもリンク修正(FR-8.1)を届けるため)。
- 将来の別データ源の足し方:
  - 読み(`kana`)・YJコード(`yjCode`)は、null を許す項目の追加で品目表に足せる(スキーマ版はそのまま)。
  - ただし、読みを検索対象にするには 5.4 の規則の変更、YJコードを L1 に使うには新しい置換記号 `{yjCode}` が要る。**どちらもアプリの更新が必要**になる。

### 5.3 データ版(`dataVersion`)
- **公開のたびに必ず新しい `dataVersion` にする**(品目表の更新でも、上書き表やテンプレートだけの更新でも)。形式は `YYYYMMDD-NN`(公開日+その日の通し番号)。
- 報告メール(FR-8.2)には `dataVersion` を入れる。どのリンク状態で起きた報告かを特定できる。
- アプリは、`dataVersion` が適用済みの版と**違えば**適用する(大小は比べない)。
- 緊急のロールバックは「古い内容を新しい `dataVersion` で公開し直す」ことで行う。

### 5.4 検索用文字列(端末で作る)
品名と成分名を、それぞれ次の処理で正規化し、改行でつないだ文字列を品目ごとに Room の別の列に保存する。検索語にも同じ処理をする。
1. NFKC 正規化(全角英数字→半角、半角カナ→全角カナ)
2. 英字を小文字に
3. ひらがなをカタカナに
4. ハイフンに似た文字(U+2010〜U+2015、U+2212)を `-` にそろえる(長音記号「ー」はそのまま)
5. 空白と「・」をすべて除く

- 「ろきそ」「ロキソ」「ﾛｷｿ」はすべて「ロキソ」になる。漢字名称の読み検索は対象外(FR-1.2 の制約のまま)。
- 品名と成分名を改行でつなぐのは、品名の末尾と成分名の先頭にまたがって誤って一致しないようにするため(検索語は 5. で空白・改行を除くので、改行を含まない)。
- 検索は `instr(search_key, :q) > 0` で行う。`LIKE` を使わないので、品名に普通に含まれる `%` や `_` がワイルドカードとして働かない。
- T08 で決めること: 件数の上限(例: 200件)、入力が落ち着いてから検索する(デバウンス)、並び順(FR-1.5。例: 品名の検索用文字列の順、同じならコード順)。

### 5.5 リンク上書き表(`link-overrides.json`)
ADR-0004 の「リンク上書き表」。品目ごとに既定のリンクを上書きする。

| 項目 | 内容 |
|---|---|
| `code` | 対象の品目コード(5.1 と同じ形式。重複不可) |
| `mode` | `L1` / `L2` / `URL`(固定 URL を使う) / `SEARCH_ONLY`(主ボタンを出さず副ボタンだけ。FR-2.5) |
| `url` | `mode` が `URL` のときだけ必須。固定の URL(5.7 の検証に通るもの) |
| `reason` | 上書きの理由(運営者向けのメモ。画面には出さない) |
| `updatedAt` | 更新日(ISO 8601) |

```json
{"overrides":[
 {"code":"1112700X1011","mode":"SEARCH_ONLY","reason":"成分一覧が空(T02 確認)","updatedAt":"2026-10-30"}]}
```

- 表に無い品目は、品目表の `defaultLink` を使う。
- 初期の上書き表は、T02 で空の一覧を確認したハロタンだけを `SEARCH_ONLY` にする。それ以外の空の一覧は、報告と定期確認で見つけて足す(ADR-0004)。

### 5.6 manifest(`manifest-v1.json`)
アプリが1日1回取得する小さなファイル(数KB)。案4-B を採る場合は、別ファイル `manifest-v1.json.sig` に manifest の署名を置く。

```json
{
  "dataVersion": "20261101-01",
  "generatedAt": "2026-11-01T03:00:00+09:00",
  "lastCheckedAt": "2026-11-02T03:00:00+09:00",
  "sources": [
    {"category": "ORAL",      "fileName": "tp20261101-01_01.xlsx", "appliedDate": "2026-11-01", "sha256": "…"},
    {"category": "INJECTION", "fileName": "tp20261101-01_02.xlsx", "appliedDate": "2026-11-01", "sha256": "…"},
    {"category": "EXTERNAL",  "fileName": "tp20261014-01_03.xlsx", "appliedDate": "2026-10-14", "sha256": "…"}
  ],
  "itemCount": {"ORAL": 7073, "INJECTION": 3479, "EXTERNAL": 1862},
  "files": {
    "items":         {"path": "items-20261101-01.json.gz", "schemaVersion": 1, "sha256": "…", "size": 233813, "uncompressedSize": 2733354},
    "linkOverrides": {"path": "link-overrides-20261101-01.json", "schemaVersion": 1, "sha256": "…", "size": 180}
  },
  "urlTemplates": {
    "l1": "https://www.pmda.go.jp/PmdaSearch/rdSearch/02/{code}?user=1",
    "l2": "https://www.pmda.go.jp/PmdaSearch/iyakuDetail/GeneralList/{code7}",
    "l3": "https://www.pmda.go.jp/PmdaSearch/iyakuSearch/"
  },
  "linkModeRemap": {}
}
```

- `sources` は区分ごとに適用日を持つ(区分ごとに更新日が違うため)。検索画面の「データ版」表示(FR-4.1)で区分ごとの日付を出すか、最も古い日を出すかは T10 で決める。
- `lastCheckedAt` は、元データに変化が無くても変換ジョブが確認するたびに更新する(FR-4.2)。このときは `dataVersion` を変えない(ファイルの中身が変わらないため。アプリは何も取り込まない)。
- `linkModeRemap` は、方式をまとめて切り替える非常用のスイッチ。例: rdSearch が全面的に使えなくなったら `{"L1": "L2"}` にして、上書き表を1万行書かずに全品目を成分一覧へ回す。上書き表で個別に指定した品目には効かない。
- l3 の既定値は、T02 で記録した検索画面の URL(ADR-0004)。末尾のスラッシュの有無で検索画面が開くかは、T11 の前に人がブラウザで確かめる。
- ファイルは版ごとに別の名前で置き、manifest だけを最後に差し替える(取得途中の端末が新旧の混ざったファイルを読まないため)。版ごとのファイルは、公開から**最低30日**残す。
- キャッシュ: manifest は短く(例: 5分)、版付きのファイルは中身が変わらないので長くキャッシュさせる。

### 5.7 アプリでの検証と適用(T09)
1. manifest を HTTPS で取得する。案4-B の場合は、同梱の公開鍵で署名を検証し、合わなければ何もしない。
2. `files.*.path` は `^[A-Za-z0-9._-]+$` のファイル名だけを許し、**同梱の配信元 URL の下**からだけ取得する(manifest の値でホストを変えられないように)。
3. `size` と `uncompressedSize` に上限(例: 圧縮後 5MB、展開後 30MB)を設け、展開中も上限を超えたら中止する。品目数にも上限(例: 5万件)を設ける。
4. 取得した全ファイルの `sha256` を確かめる。
5. **manifest に載った全ファイルの取得と検証が済んでから、1つの Room トランザクションで品目表・上書き表・URL テンプレート・`linkModeRemap`・適用した `dataVersion` をまとめて切り替える**。途中で失敗したら何も切り替えず、直前のデータを使い続ける(FR-3.4)。
6. 「最終同期日時」(FR-4.2、FR-4.3 の7日警告)は、**manifest の確認に成功し、必要なら適用まで終わった日時**とする(データに変化が無い日も更新する)。

### 5.8 リンクの組み立てと検証(T11)
- 主ボタンの方式は「上書き表 → 品目表の `defaultLink` → `linkModeRemap`」の順に決める。未知の方式は `SEARCH_ONLY` とする。副ボタン(L3)は全品目に出す。
- 置き換える記号は `{code}`(12文字)と `{code7}`(上7文字)だけ。`code` は 5.1 の形式に合うものだけを使う。
- **URL の検証は置き換えた後に行う。** URI として解析し、scheme が `https`、host が `www.pmda.go.jp` と完全一致、userinfo とポートが無いことを確かめる。
- 検証に通らないときの戻り先:
  - テンプレートが不正: 同梱の既定テンプレートを使う。
  - 上書き表の固定 URL(`mode=URL`)が不正: その品目の `defaultLink` を使う。
- テンプレートの既定値はアプリにも同梱する。アプリのコードに PMDA の URL を書くファイルは、そのとき `scripts/ci/pmda-allowlist.txt` に1行で追加する(T04 の検査)。

### 5.9 同梱データ(T08)
- APK の assets に、配信と同じ一式(manifest・品目表・上書き表)を入れる。
- 起動時に、同梱の `dataVersion` と適用済みの `dataVersion` を比べる。まだ何も適用していない、または同梱の `generatedAt` の方が新しい(アプリ更新で同梱データが新しくなった)ときは、同梱を 5.7 の 4〜5 と同じ手順で取り込む。
- 初回の取り込み(約1秒の見込み)はメインスレッドで行わない。完了までの画面の状態は T08 で決める。

### 5.10 変換ジョブの品質ゲート(T06・T07 で実装)
次のどれかに当てはまれば公開せず、運営者に通知する。
- 期待する見出し(区分・コード・成分名・規格・品名・メーカー名・先発/後発の列)が位置どおりに見つからない(ふりがな付きの見出しは、ふりがなを除いて照合する)
- コードが形式に合わない、重複がある、必須の文字列が空
- 区分ごとの件数が前回より 5% を超えて減った
- `defaultLink` が `L1` の品目の割合が前回から 5 ポイントを超えて変わった
- 前回のデータが無い初回は、前回比の検査の代わりに、区分ごとの件数が下限(例: 内用 5,000・注射 2,000・外用 1,000)以上であることを確かめる
- 上書き表: JSON の形、コードの形式と重複、`mode` の値、`mode=URL` のとき `url` があり 5.8 の検証に通ること。**上書き表だけを配信するとき(T07)も同じ検査を通す**
- URL テンプレート: 5.8 の検証に通ること

## 影響・結果
- ロードマップの「Room+FTS」と「インデックス(圧縮 SQLite)」は、この ADR の決定(部分一致検索、gzip JSON)に置き換える。
- ADR-0002 第2版の「インデックス(圧縮 SQLite)」は、この ADR で置き換える。
- 同梱データのサイズは約 230KB(gzip)で、APK への影響は小さい。
- 案4-B を採る場合、T07 に署名の処理、T09 に検証の処理が加わる(約0.5日)。署名の秘密鍵は CI シークレットだけに置き、リポジトリに入れない(CLAUDE.md)。鍵を失ったときの手順は runbook に書く。
